# 鸿蒙小程序容器实战 02 独立 HAR 构建与宿主集成

SDK 迁移中一个容易忽略的问题是：宿主能够引用源码模块，并不代表独立 HAR 已经可以交付。

这次项目最终要求 `entry` 消费打包后的 `mpsdk.har`。因此我把构建目标拆成两段：先证明 SDK 能产出 HAR，再证明新宿主实际使用这个产物构建和运行。

本文讲的都是本工程的构建组织方式，工具链基线为 DevEco Studio 6.1.1 与 API 24。

## 先解决首次构建的依赖顺序

宿主最终依赖如下：

```json
{
  "dependencies": {
    "mpsdk": "file:../libs/mpsdk.har"
  }
}
```

但新克隆仓库时，`libs/mpsdk.har` 还不存在。它是生成产物，没有进入 Git。此时直接同步宿主依赖，就会遇到“需要 HAR 才能同步，但 HAR 又需要先构建”的顺序问题。

我的处理方式是在构建脚本中增加一个引导阶段：临时选择源码模块，完成 SDK 构建，再切换到打包 HAR。

```text
选择 file:../mpsdk
        ↓
OHPM 同步源码依赖
        ↓
构建 mpsdk.har
        ↓
复制到 libs/mpsdk.har
        ↓
选择 file:../libs/mpsdk.har
        ↓
重新同步依赖
        ↓
构建宿主 HAP
```

顺序明确后，读者第一次拿到仓库，就有一条从源码开始的构建入口，而不是依赖作者电脑上恰好残留的 HAR。

## 用一个小工具负责依赖切换

`tools/sdk-dependency.cjs` 只负责修改当前项目的依赖字段。核心代码节选如下：

```javascript
manifest.dependencies.mpsdk = mode === 'source'
  ? 'file:../mpsdk'
  : 'file:../libs/mpsdk.har';
```

这个工具不执行编译，也不负责签名。它的职责越小，就越容易在失败时明确恢复到哪个状态。

另一个维护规则同样重要：SDK 修改发生在 `mpsdk/`，随后重新构建 HAR。不要直接修改 `oh_modules` 里的解包副本，否则下一次同步就可能覆盖修改，也很难解释最终产物来自哪里。

## 配置正确还要检查实际解析结果

依赖清单切成 HAR 后，如果本地解析仍然指向源码目录，构建可能继续成功，但这个成功无法证明 HAR 消费链路。

我在根 `hvigorfile.ts` 加了一道检查：清单声明打包 HAR 时，读取已安装 `mpsdk` 的真实路径；如果它仍然等于源码模块路径，就终止构建，提示重新同步 OHPM。

这里比较的是 `realpath`，因为需要识别本地链接实际落到了哪里。它检查的是本项目已知的源码链接残留问题，并不是通用的依赖供应链审计。

这个检查把“清单看起来正确”推进到了“本地解析没有继续使用那条源码链接”。后面再通过打包 HAR 的签名 HAP 构建与真机运行确认交付路径。

## 构建失败后也要有明确状态

一次构建可能在 OHPM 同步、HAR 编译、文件复制或 HAP 编译的任意阶段失败。如果脚本直接退出，工作区可能停留在临时源码依赖状态。

下一次从 IDE 点击构建时，开发者很容易忘记上一次失败发生在哪里。

所以脚本在 `finally` 中处理失败恢复：如果引导过程开始了却没有完成，就恢复打包 HAR 的依赖配置；当本地产物存在时，再尝试同步解析结果。同步仍失败则明确提醒后续需要 OHPM 同步。

用伪代码表达这个过程：

```text
try
    切源码 → 同步 → 构建 HAR → 切产物 → 同步 → 构建 HAP
finally
    如果流程中断
        恢复打包依赖清单
        在具备产物时尝试恢复本地解析
        对未恢复部分给出提示
```

恢复配置不等于修复编译错误。首次构建如果还没生成 HAR 就失败，后续仍需修正原因，再从引导流程重新开始。

## 将工具链路径收敛到一个入口

迁移中曾出现构建进程缺少 Java 路径的问题。我没有把本机安装路径写进公共工程，而是让脚本从 `DEVECO_STUDIO_HOME` 推导 SDK、JBR、OHPM 和 TypeScript 路径。

设置本机环境变量后，项目提供三个入口：

```powershell
# 生成 HAR，并切回打包依赖
./tools/build.ps1 -Task Har

# 生成 HAR，再构建宿主 HAP
./tools/build.ps1 -Task Hap

# 执行限定范围的迁移回归
./tools/build.ps1 -Task Tests
```

TypeScript 路径主要服务于当前 Node 回归中的源码加载。它与设备上的 ArkTS 编译、系统能力验收不是同一层检查。

## 签名配置与公共代码分开保存

项目公开的是构建逻辑和签名模板，本机签名放在 Git 忽略的 `.local/signing.json` 中。

根构建逻辑读取本地配置，再注入构建上下文；没有本地签名时生成 unsigned HAP。读者需要使用自己的签名配置才能完成对应设备安装。

这样组织的好处是，更换机器或协作者时可以保留同一套构建脚本，而不用把证书路径、设备信息和私有签名跟着提交。

需要额外说明的是，将当前配置移出 Git 不会自动清理已有历史。这是当前文件管理和历史管理的区别。

## 迁移时保留运行模块并剥离环境配置

原 SDK 中有本次没有启用的厂商模式和能力。迁移首轮我保留了必要模块、资源和静态依赖，没有同时进行大规模裁剪。

这样可以把问题拆开：先证明现有 SDK 在新宿主里能打包和运行，再判断哪些模块适合精简。否则资源缺失、类型引用和协议初始化可能同时变化，很难定位回归来源。

保留代码也不意味着完成了对应能力验收。例如，LINE CLIENT 账号模块随 SDK 保留，但当前宿主使用的是 WEB 模式。

宿主部分则保留目标工程自己的 AppScope 和产品配置，不搬入原工程的完整目录、卡片、广告 UI、元服务胶囊或保活栈。证书、签名、设备信息、登录态、IDE 配置和依赖缓存也没有作为 SDK 迁移内容复制。

这样既保住了 SDK 的运行依赖，也避免把源宿主的产品结构和本机环境一起带入。新增宿主只需要消费约定好的 HAR 接口。

## 我怎样判断这条构建链路完成了

本次先后确认了 HAR 构建、源码依赖宿主构建、打包 HAR 宿主签名构建，并在 API 26 真机完成安装与选定流程。

这支持“新宿主能够消费独立 HAR”的结论。后续还可以在另一台机器或干净目录复现，进一步检查环境依赖。

编译告警、原 SDK 的既有测试失败则单独记录。工程交付需要知道哪些检查已完成，也需要保留还没有解决的问题。
